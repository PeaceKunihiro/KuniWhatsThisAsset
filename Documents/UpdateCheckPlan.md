# バージョン情報からの更新確認案

検討日：2026-11-16。対象は現在のv0.6.0。当初の検討案に基づきv0.7.0で実装済み。

## 提案する動作

ユーザーがHelp→バージョン情報を開いたときだけ、必要に応じてGitHubのmaster/Stableを確認する。起動時やパッケージ読み込み時には確認しない。

| 状態 | 動作・表示 |
| --- | --- |
| 当日未試行 | アイコン・現在版・Stableリンクを即表示し、非同期で1回確認 |
| 新しい正式版あり | ダイアログ内に「新しいバージョン vX.Y.Z」とダウンロードボタンを表示 |
| 同じ版、または公開版のほうが古い | 更新通知を出さずStableリンクのみ表示 |
| 当日試行済み | 通信せずStableリンクのみ表示。既知の更新情報も再通知しない |
| 接続不能、タイムアウト、404、API制限、応答不正、対象ZIPなし | エラーダイアログを出さずStableリンクのみ表示 |

「リンクのみ」は更新確認に関する追加表示を指し、既存のアイコン・現在のバージョン番号・閉じるボタンは維持する。Stableリンクは常に同じ固定URLとし、更新確認の成否に関係なくユーザー操作でブラウザを開けるようにする。オフライン時の閲覧成功を保証する意味ではない。

通知を別のMessageBoxにせず、バージョン情報内で完結させる。ダウンロードはユーザーがボタンを押した場合に既定ブラウザで行う。アプリが自動ダウンロード・ZIP展開・インストール・実行中EXEの置換を行う仕組みは含めない。

## 1日1回の定義案

「PCの現地日付ごとに1回の確認試行」とする。失敗した場合も当日の試行に数え、ダイアログを閉じて開き直しても再確認しない。翌日、再びバージョン情報を開いたときに確認する。24時間間隔方式ではなく、日付で区切るという設計上の解釈を明示する。

ユーザー別のLocalApplicationData/KuniWhatsThisAsset/update-check.jsonへ最終試行日・UTC時刻を保存し、アプリ再起動・本体フォルダー移動後も維持する。配布ZIPへ状態ファイルを混入させない。確認日を通信前に確定・永続保存し、失敗・キャンセルでも取り消さない。同時起動間でもロックして1回に制御する。既に別インスタンスが確認中ならリンク表示だけとする。

状態を確実に保存できない場合は、同日の繰り返し通信を避けるため確認を行わずStableリンクを表示する。最終試行日が未来の場合も再試行しない。状態の破損・端末の時刻やタイムゾーン変更・手動削除時の取り扱いは実装テストに含める。

## 更新情報の取得と判定

確認対象：
https://github.com/PeaceKunihiro/KuniWhatsThisAsset/tree/master/Stable

機械的な確認はHTMLのスクレイピングではなく、公開リポジトリのGitHub Contents APIを使用する。

GET https://api.github.com/repos/PeaceKunihiro/KuniWhatsThisAsset/contents/Stable?ref=master

調査時点でv0.1.0〜v0.6.0のwin-x64 ZIPとSHA256ファイルを確認できた。認証トークンをアプリへ埋め込まず、公開リソースとしてアクセスする。

- ファイル名がKuniWhatsThisAsset-v{major}.{minor}.{patch}-win-x64.zipに完全一致し、type=fileの項目のみを対象にする。
- 版は3つの非負整数として比較し、文字列順・更新日時順・配列の末尾では判定しない。0.10.0は0.9.0より新しい。
- 現在版はビルドのバージョン情報から取得し、ダイアログ表示用文字列と別にハードコードしない。
- プレリリース名や別アーキテクチャ、不正な名前、.sha256単体は最新版として扱わない。
- 更新通知は公開最新版が現在版より大きい場合だけ表示する。開発版のほうが新しい場合もダウングレードを促さない。
- 通信は非同期、短いタイムアウト（案：5秒）、自動再試行なしとする。応答サイズと項目数にも上限を設け、ダイアログ終了時は結果反映を中止する。

Contents APIはディレクトリ一覧が1,000項目までという制限を持つ。長期的にはStable/latest.json等の単一メタデータに切り替える余地があるが、初回実装で新しい公開ファイルを必須にはしない。

## ダウンロード

初回確認で得た最新版ZIPのダウンロード先を、ユーザー操作で既定ブラウザに渡す。HTTPSかつ当該GitHubリポジトリのStable内に限定し、API応答中の任意URLをそのまま実行しない。ブラウザ起動にはファイル名やコマンドを連結せず、検証したURIのみを渡す。

GitHub公式資料ではdownload_urlはキャッシュ再利用を前提としないため、長期保存せず今回取得した結果にだけ使用する。同日再表示時は仕様通りStableへの固定リンクだけとする。ダウンロードのために利用者がブラウザで操作する通信は「アプリによる1日1回の自動確認」とは別に扱う。

最初はブラウザダウンロードを採用するため、アプリ内SHA256自動検証は行わない。アプリ内ダウンロードを将来追加する場合は、保存先指定・一時ファイル・キャンセル・対応SHA256による検証を別途実装する。同じ公開元のチェックサムは改変・破損確認の手掛かりであり、公開元の真正性を署名のように保証するものとは扱わない。

## 既存方針への影響

- アイコンと現在のバージョン表示を残し、下部に更新欄とStableリンクを追加する。内容が切れないようダイアログの高さも調整する。
- パッケージ解析は従来通り外部送信しない。今回のGitHub更新確認だけをユーザー起点の通信として区別し、README・Helpに明記する。
- パッケージ内のスクリプト・URL・ファイル名を更新確認先やダウンロード先に使わない。
- 新しい依存パッケージを増やさず、.NET標準HttpClient・JSON・既定ブラウザ起動で構成できる見込み。実装時に検証する。
- v0.7.0として実装。ZIPはStable/へ出力する。

## 実装時の検証項目

- 新版あり／同版／旧版／0.9.0と0.10.0／不正名／別CPU／ZIP欠落。
- 当日の初回・再表示・失敗後再表示・再起動・同時起動・翌日・時計戻し。
- 状態保存失敗・破損、DNS/接続失敗、API制限、5秒タイムアウト、不正JSON。
- 通信中に閉じる、同時に開く、ダウンロードリンクの検証とブラウザ起動失敗。
- 失敗時も既存のバージョン情報が表示され、追加のエラーダイアログが出ない。

## 実装・検証結果（2026-11-16）

UpdateCheckerとFileUpdateAttemptStoreを実装。FileShare.Noneで状態ファイルを排他し、通信前に確認日を書き込んでディスクへフラッシュする。既存の空・破損状態や保存不能・未来日は通信を抑制する。HTTPはリダイレクトを自動追跡せず、5秒・応答1 MiB・一覧1,000項目を上限とする。版とダウンロード先を検証し、AboutWindowの生存中だけ結果を反映する。

モックHTTPによるテストで数値比較、URL制限、失敗後の同日抑制、翌日の確認、並行確認、JSON不正・通信失敗・キャンセルを確認。WPFでは新版通知と同日再表示時のリンクのみ表示を確認した。実ブラウザのダウンロードと実ネットワークの障害ケースは未検証。

## v0.11.0での拡張（2026-11-16）

手動の「更新を確認する」は自動の日次制限を解除する。日次記録は従来どおり更新し、自動確認の重複は抑制する。結果はダイアログ内へ表示し、Stableへの固定リンクも維持する。

「ダウンロードして更新・再起動」はユーザー操作時のみ開始する。ZIPとSHA256、ZIP内のLibs/distribution.jsonを検証してから別プロセスへ渡す。設定ファイル・履歴・ブックマーク・キャッシュは更新対象に含めない。helperがREADYを返すまで本体を終了せず、終了待ち・置換・失敗時復元・再起動を行う。

v0.11.0以降の配布形式を対象とする。GitHub StableにはZIPと.sha256を同時に配置する。古い配布形式やネットワーク問題は手動取得用リンクで補完する。新規の検証は61件のCoreチェック、WPFの手動/進捗/エラー/キャンセルと、隔離した発行版の実プロセス置換・再起動で行う。実際のGitHub最新版配布物の公開・アップロードはこの実装作業に含めない。
